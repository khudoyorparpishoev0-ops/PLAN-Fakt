# Аудит базы данных

## Схема

26 моделей, 13 миграций. Применены на **чистой** базе `qa_migrate` с нуля —
успех; повторный `migrate deploy` — «No pending migrations». Расхождения между
миграциями и `schema.prisma` нет: `prisma migrate diff` → «No difference detected».

## Ключи и связи

Первичные ключи — целочисленные автоинкременты. Внешние ключи объявлены на
все связи. Уникальные ограничения там, где они значат правило предметной
области: `operations.external_ref` (идемпотентность одобрения),
`requests.number`, `deals.number`, `projects.name`, `users.email`,
`exchange_rates(currency_code, rate_date)`.

Индексы на `operations`: `date`, `project_id`, `article_id`, `deal_id`,
уникальный `external_ref`. `EXPLAIN ANALYZE` на выборке план-факта за год —
2,4 мс на 10 025 строк; узкое место не в базе (см. `14_PERFORMANCE_AUDIT.md`).
Дополнительные индексы не нужны.

## Мягкое удаление

`deleted_at` есть у всех финансовых сущностей. Обычные выборки фильтруют по
`deleted_at is null`; история и аудит остаются. Проверено: статью с операциями
удалить нельзя вовсе (422), операции удалённых сущностей из отчётов не пропадают.

## Целостность

Поиск «сирот» на демо-базе:

| Проверка | Результат |
| --- | --- |
| Операции без проекта | есть — допустимо (общефирменные расходы) |
| Операции с несуществующей статьёй | нет |
| Поставки без сделки | нет |
| Заявки без автора | нет |
| Записи аудита без пользователя | нет |

Nullable-поля соответствуют предметной области: у поездки нет суммы, у
операции может не быть проекта или счёта.

## Транзакции

В транзакции обёрнуты: одобрение заявки (статус + плановая операция),
сторнирование, создание поставки с приходами на склад, удаление поставки,
сохранение сетки планов. Ситуация «операция создалась, заявка осталась
прежней» невозможна.
