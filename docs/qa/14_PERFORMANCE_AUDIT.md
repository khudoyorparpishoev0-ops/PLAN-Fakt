# Аудит производительности

Метод: в базу вставлено 10 000 операций 2026 года (пометка `TEST-QA-perf-`),
сняты времена ответа, данные удалены. Замеры — `curl --write-out time_total`.

| Запрос | 100 операций | 10 000 операций |
| --- | --- | --- |
| `GET /operations?limit=50` | — | **0,03 с** |
| `GET /operations?limit=50&q=…` | — | 0,03 с |
| `GET /projects` | — | 0,01 с |
| `GET /clients` | — | 0,04 с |
| `GET /plans/grid?year=2026` | — | 0,08 с |
| `GET /deals` | — | 0,02 с |
| `GET /stock` | — | 0,01 с |
| `GET /planfact?from&to` | **0,03 с** | **0,9–1,7 с** |
| `GET /export/operations.xlsx` | — | 3,5 с (390 КБ) |

## Где узкое место

Не в базе. `EXPLAIN (ANALYZE, BUFFERS)` на выборке план-факта:

```
Seq Scan on operations (actual time=0.009..2.430 rows=10025 loops=1)
Buffers: shared hit=217
```

2,4 мс. Время уходит на то, что Prisma материализует все операции периода со
связями (статья, проект, контрагент), а свод считается в JavaScript. Плюс при
заданном периоде расчёт выполняется дважды — для текущего периода и для
предыдущего (сравнение прибыли).

## Запросов на страницу

Проверка на N+1: циклов с запросом внутри в путях чтения нет. Единственный
такой случай был в справочнике валют (запрос курса на каждую из 156 валют) и
устранён до аудита. Списки грузятся двумя-четырьмя запросами независимо от
числа строк.

## Вывод

Списки и справочники держат десять тысяч записей без замечаний. План-факт
растёт линейно: при нескольких тысячах операций в год годовой отчёт
открывается около секунды. Это терпимо сейчас и станет заметно через
несколько лет — рекомендация по переносу свода в SQL записана как PERF-001.
