# Выкладка фронтенда IT-HONA «Финансы План-Факт» (ШАГ 0)

Целевой сервер: Ubuntu 22.04, установлены Docker / Docker Compose, PostgreSQL 16
и MinIO уже запущены; существуют `/opt/app/docker-compose.yml` и `/opt/app/.env`.
Все команды выполняются на сервере от пользователя с правами sudo.
Единственная подстановка — домен в разделах 3 и 5 (пока домена нет, работаем по IP).

---

## Быстрый путь — одна команда (`deploy.sh`)

Скрипт `deploy.sh` в корне репозитория разворачивает ВЕСЬ стек (фронтенд +
бэкенд + БД-миграции) сам:

- ставит git/nginx/curl при отсутствии, проверяет Docker;
- клонирует или обновляет `/opt/app/app`;
- дописывает недостающие переменные в `/opt/app/.env` (существующие значения
  не перезаписывает; `DATABASE_URL` собирает из `POSTGRES_*`, недостающие
  секреты — `JWT_SECRET`, `SEED_PASSWORD_*` и т.п. — генерирует);
- дописывает сервисы `backend` и `frontend` в `/opt/app/docker-compose.yml`,
  не трогая существующие postgres/minio (перед правкой делает `.bak`,
  после — проверяет файл через `docker compose config`);
- собирает и поднимает контейнеры, выполняет `prisma migrate deploy` и
  идемпотентный seed;
- настраивает системный nginx (`/` → :8080, `/api/` → :3000) и проверяет
  `http://localhost/` и `http://localhost/api/health`.

Идемпотентен — повторный запуск обновляет развёрнутое, дублей не создаёт.

Если репозиторий доступен серверу напрямую (публичный или с настроенным доступом):

```bash
sudo sh -c "$(curl -fsSL https://raw.githubusercontent.com/khudoyorparpishoev0-ops/PLAN-Fakt/refs/heads/claude/design-handoff-implementation-3okq4o/deploy.sh)"
```

Либо скопируйте один файл `deploy.sh` на сервер любым способом (scp и т.п.) и:

```bash
sudo sh deploy.sh
```

Параметры (по умолчанию — текущий репозиторий и ветка
`claude/design-handoff-implementation-3okq4o`); для приватного репозитория
передайте URL с токеном:

```bash
sudo sh deploy.sh https://<TOKEN>@github.com/khudoyorparpishoev0-ops/PLAN-Fakt.git claude/design-handoff-implementation-3okq4o
```

Успешное завершение печатает: `ГОТОВО, откройте http://<IP>/`.
При ошибке скрипт называет шаг, на котором остановился, и команды диагностики.

## Подробные шаги (запасной вариант, вручную)

## 1. Клонирование репозитория

```bash
sudo mkdir -p /opt/app
cd /opt/app
git clone https://github.com/khudoyorparpishoev0-ops/PLAN-Fakt.git app
cd /opt/app/app
git checkout claude/design-handoff-implementation-3okq4o
```

Обновление до свежей версии в дальнейшем:

```bash
cd /opt/app/app && git pull
```

## 2. Сборка и запуск контейнера фронтенда

```bash
cd /opt/app/app
docker compose -f docker-compose.frontend.yml up -d --build
```

Проверка, что контейнер поднялся и отвечает локально:

```bash
docker ps --filter name=it-hona-frontend
curl -I http://127.0.0.1:8080/
```

Ожидаемо: контейнер в статусе `Up`, ответ `HTTP/1.1 200 OK`.

Пересборка после обновления кода:

```bash
cd /opt/app/app && git pull && docker compose -f docker-compose.frontend.yml up -d --build
```

## 3. Системный nginx (проксирование на контейнер)

Шаблон `server-setup/03_nginx/crm.conf.example` в репозитории отсутствует —
конфиг приведён целиком ниже. Создать файл:

```bash
sudo tee /etc/nginx/sites-available/crm.conf > /dev/null <<'EOF'
server {
    listen 80;
    listen [::]:80;
    # Пока домена нет — ловим все обращения по IP; после выпуска домена
    # заменить `_` на имя, например: server_name crm.example.tj;
    server_name _;

    client_max_body_size 12m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Задел под backend (шаг 1): начнёт работать после запуска сервиса на :3000
    location /api/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
EOF
```

Включить сайт и перечитать конфигурацию:

```bash
sudo ln -sf /etc/nginx/sites-available/crm.conf /etc/nginx/sites-enabled/crm.conf
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
```

## 4. Проверка

```bash
curl -I http://localhost/
```

Ожидаемо: `HTTP/1.1 200 OK` (отдаёт index.html приложения через прокси).
В браузере по IP сервера открывается экран входа; интерфейс (админ-панель
или кабинет бухгалтера) определяется ролью учётной записи (ШАГ 2).

## 5. Сертификат TLS — выполнить позже, когда появится домен

> Раздел отложен: домена ещё нет. После делегирования домена на IP сервера:

```bash
# 1) вписать домен в server_name в /etc/nginx/sites-available/crm.conf
sudo apt-get install -y certbot python3-certbot-nginx
sudo certbot --nginx -d crm.example.tj   # подставить реальный домен
sudo systemctl reload nginx
```

Certbot сам добавит 443-блок и редирект с http. Автопродление проверяется:

```bash
sudo certbot renew --dry-run
```

# Бэкенд (ШАГ 1): API + PostgreSQL

Бэкенд — NestJS + Prisma, каталог `server/`. Слушает `127.0.0.1:3000`, наружу
не публикуется: системный nginx из раздела 3 уже проксирует `/api/` на
`127.0.0.1:3000`. Использует существующие PostgreSQL и MinIO из
`/opt/app/docker-compose.yml`.

> **Быстрый путь:** всё, что описано ниже (env, сервисы compose, сборка,
> миграции, seed, проверка), автоматически делает `deploy.sh` — см. раздел
> «Быстрый путь» в начале документа. Ручные шаги ниже — запасной вариант
> и справка о том, что именно происходит.

## 1. Переменные окружения

Дополнить `/opt/app/.env` (имена — как в `server/.env.example`; уже существующие
значения не менять):

```bash
# хост postgres = имя сервиса в /opt/app/docker-compose.yml
DATABASE_URL=postgresql://<PG_USER>:<PG_PASSWORD>@postgres:5432/<PG_DB>?schema=public
JWT_SECRET=<случайная строка, понадобится на шаге 2>
TZ=Asia/Dushanbe
# пароли тестовых пользователей для seed (иначе будут сгенерированы и напечатаны)
SEED_PASSWORD_ADMIN=<пароль администратора>
SEED_PASSWORD_DIRECTOR=<пароль директора>
SEED_PASSWORD_ACCOUNTANT=<пароль бухгалтера>
```

## 2. Сервисы в /opt/app/docker-compose.yml

В существующий `/opt/app/docker-compose.yml` (рядом с postgres и minio; там есть
заготовка в комментариях) добавить:

```yaml
  backend:
    build:
      context: /opt/app/app
      dockerfile: server/Dockerfile
    env_file: /opt/app/.env
    ports:
      - "127.0.0.1:3000:3000"
    restart: unless-stopped
    depends_on:
      - postgres

  frontend:
    build:
      context: /opt/app/app
      dockerfile: Dockerfile
    ports:
      - "127.0.0.1:8080:80"
    restart: unless-stopped
```

Имя `postgres` в `depends_on` и в `DATABASE_URL` — фактическое имя сервиса
PostgreSQL из вашего compose-файла (подставить, если отличается).

Если фронтенд ранее был запущен скриптом `deploy.sh` (одиночный контейнер
`it-hona-frontend`), перед `docker compose up` удалить его, чтобы не конфликтовал
порт: `docker rm -f it-hona-frontend`.

## 3. Сборка, запуск, миграции, seed

```bash
cd /opt/app/app && git pull
cd /opt/app
docker compose up -d --build backend frontend
docker compose exec backend npx prisma migrate deploy
docker compose exec backend npm run seed
```

Seed идемпотентен — можно запускать повторно. Если `SEED_PASSWORD_*` не заданы,
случайные пароли печатаются в вывод один раз — сохраните их.

Пароли из seed — **временные** (`must_change_password = true`): при первом
входе интерфейс потребует их сменить (форсирование входа — на шаге 2 вместе
с авторизацией; форма смены пароля в интерфейсе уже есть). Правила
обновления при повторном seed:

- значение `SEED_PASSWORD_*` изменилось → пароль пользователя обновляется
  (снова помечается временным);
- значение не изменилось → хэш не переписывается;
- пользователь уже сменил пароль в интерфейсе (`password_changed_at`
  заполнен) → seed его пароль **не трогает** и пишет предупреждение.

## 4. Проверка

```bash
curl http://127.0.0.1:3000/api/health
# → {"status":"ok","db":"ok","time":"..."}
curl http://localhost/api/health   # через системный nginx
```

В базе после seed: проекты, учётные статьи, контрагенты, счета, операции и
заявки — те же, что сейчас отображает интерфейс на фикстурах. Быстрая сверка:

```bash
docker compose exec postgres psql -U <PG_USER> -d <PG_DB> -c \
  "SELECT count(*) AS projects FROM projects; SELECT count(*) AS requests FROM requests;"
```

Примечание: фронтенд к API пока не подключён (шаг 3) — интерфейс продолжает
работать на фикстурах; бэкенд отдаёт только `/api/health`.

# Авторизация (ШАГ 2)

Вход по email/паролю (bcrypt), JWT access (15 мин) + refresh (7 дней), роль в
токене. Интерфейс: admin и director → админ-панель, accountant → кабинет
бухгалтера. Демо-переключатель ролей удалён — вместо него настоящие вход и
выход. Пока `must_change_password = true` (временный пароль из seed), сервер
отвечает 403 `password_change_required` на все защищённые эндпоинты, а
интерфейс форсирует экран смены пароля.

Требование: `JWT_SECRET` в `/opt/app/.env` обязателен (в production без него
backend не стартует). TTL настраиваются `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL`
(необязательные).

Эндпоинты: `POST /api/auth/login`, `POST /api/auth/refresh`,
`GET /api/auth/me`, `POST /api/auth/password`, `GET /api/users` (только admin).
Выход — на клиенте (токены удаляются; серверного отзыва токенов нет — при
компрометации сменить JWT_SECRET).

Проверка после деплоя:

```bash
# вход (вернёт токены и пользователя; при временном пароле mustChangePassword=true)
curl -s -X POST http://localhost/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"admin@it-hona.tj","password":"<SEED_PASSWORD_ADMIN>"}'

# чужой эндпоинт возвращает 403: возьмите accessToken бухгалтера и вызовите
curl -s -w '\n%{http_code}\n' http://localhost/api/users -H "Authorization: Bearer <ACCESS_БУХГАЛТЕРА>"
# → {"error":{"code":"forbidden",...}} 403
```

# Данные из API (ШАГ 3)

Интерфейс работает на реальных данных БД: кабинет бухгалтера (заявки —
создание/список/удаление черновика, проекты, ставка км), админ-панель
(журнал операций, план-факт, «Требует внимания» с настоящим одобрением,
справочники). Одобрение заявки директором создаёт **плановую операцию
расхода** по проекту (ТЗ, п. 8) — она видна в журнале (тег «План») и в
план-факте.

Эндпоинты (все под JWT; чужая роль получает 403):

| Метод и путь | Кому | Что |
|---|---|---|
| `GET /api/requests?kind=&status=` | бухгалтер (только свои) · директор · админ | список заявок |
| `POST /api/requests` | бухгалтер | создать заявку (сразу «Отправлено») |
| `PATCH /api/requests/:id/status` | директор · админ | `review` / `approved` / `rejected`; одобрение создаёт плановую операцию; одобренная заявка неизменяема |
| `DELETE /api/requests/:id` | бухгалтер (автор) | удалить, только «Черновик» |
| `GET /api/operations` | директор · админ | журнал операций |
| `GET /api/planfact` | директор · админ | строки план-факта (доходы/расходы) |
| `GET /api/projects` | все роли | проекты (метаданные) |
| `GET /api/dictionaries` | директор · админ | статьи, контрагенты, счета, юрлица, товары, услуги |
| `GET /api/settings` | все роли | `{ kmRate }` — ставка компенсации, сомони/км |
| `PATCH /api/settings` | админ | задать ставку: `{"kmRate": 1.5}` |

Деплой той же одной командой `deploy.sh`: миграция
`step3_planfact_display_settings_goods_services` и обновлённый seed
применяются автоматически (`prisma migrate deploy` + `npm run seed`).

Ставка компенсации поездок хранится в БД (`settings.km_rate`, дирам/км),
по умолчанию 0 — поездки показываются в километрах. Задать (пример 1,50
сомони/км):

```bash
curl -s -X PATCH http://localhost/api/settings -H 'Content-Type: application/json' \
  -H "Authorization: Bearer <ACCESS_АДМИНА>" -d '{"kmRate":1.5}'
```

Сквозной сценарий приёмки (ТЗ, п. 11) — проверить в браузере:

1. Войти бухгалтером → «Заявки на оплату» → заполнить форму → отправить
   (появится в «МОИ ПОСЛЕДНИЕ ЗАЯВКИ» со статусом «Отправлено»).
2. Выйти, войти директором → «Показатели» → «Требует внимания» →
   «Ждёт вашего согласования … заявка З-NNN» → «Согласовать».
3. «Операции»: появилась строка «Заявка З-NNN · …» с тегом «План»;
   «План-Факт»: категория заявки в блоке расходов.
4. Снова бухгалтером: у заявки решение «Одобрено».

# Периоды, фильтры и справочники (завершение этапа 1)

- `GET /api/planfact?from=YYYY-MM-DD&to=YYYY-MM-DD` — план-факт за период
  плюс блок `metrics`: остатки касс и счетов, ожидаемые поступления,
  предстоящие выплаты, свободный остаток, кассовый разрыв, дебиторская и
  кредиторская задолженность с просрочкой, перерасход, экономия, прогноз,
  прибыль прошлого периода. Карточки «Деньги» и «Задолженности» на
  «Показателях» больше не константы.
- Переключатель «День / Неделя / Месяц / Квартал / Год» в интерфейсе
  фильтрует данные; по умолчанию — «Год» (см. `docs/CABINET_DIFF.md`).
- Справочники: `POST /api/dictionaries/:kind`,
  `PATCH /api/dictionaries/:kind/:id`, `DELETE /api/dictionaries/:kind/:id`,
  где `:kind` = `counterparty | account | entity | good | service | article`.
  Системные статьи и записи, на которые ссылаются операции, удалить нельзя —
  сервер отвечает 422 с пояснением (ТЗ, п. 8).
- Проекты: `POST /api/projects` (создание), `PATCH /api/projects/:id`
  (карточка и/или архив). В интерфейсе — «+ Проект» и «Редактировать».
- Заявки: `PATCH /api/requests/:id` — правка автором в статусах «Черновик»
  и «Отклонено», с `resend: true` заявка уходит директору заново
  (в кабинете — «Исправить и отправить снова» в карточке заявки).

Счета в справочнике получили вид (касса / расчётный счёт) и входящий
остаток — их разбирает seed из подписей вида «Расчётный счёт · остаток
512 600 смн». Для нового счёта вид выбирается в форме.

# ШАГИ 4–7: вложения (MinIO), сторнирование, журнал, проекты, Excel, администрирование

## Вложения (ШАГ 4)

Файлы заявок (счёт / фото одометра / чек — JPG/PNG/PDF до 10 МБ) загружаются
в **MinIO** через S3-API: `POST /api/uploads` → ключ → передаётся в
`POST /api/requests`; скачивание — `GET /api/attachments/:id` (бухгалтер —
только свои). Backend сам создаёт бакет при старте. Переменные уже
прописывает `deploy.sh` (`S3_ENDPOINT=http://minio:9000`, `MINIO_*`).
Если `S3_ENDPOINT` не задан — файлы пишутся в каталог `STORAGE_DIR`
(запасной вариант; в docker-контейнере без тома файлы не переживут
пересборку — используйте MinIO).

Имена вложений из seed — заглушки без файлов: интерфейс подскажет
«демо-имя, файла нет». Реальные файлы появляются у новых заявок.

## Сторнирование (ШАГ 4)

`PATCH /api/requests/:id/storno` (директор/админ): плановая операция
гасится обратной записью `req:<номер>:storno` (история в журнале
сохраняется), строка план-факта получает статус «Сторнировано» с планом 0.
В интерфейсе — кнопка «Сторнировать» в карточке строки «План · заявка …»
(экран «Расходы», открывается по клику на строку).

## Журнал операций (ШАГ 5)

- `GET /api/operations` — серверные фильтры (ТЗ, п. 9): `type[]`,
  `confirmed`, `date_from/to`, `account`, `counterparty`, `article`,
  `project`, `amount_min/max`, `q`; пагинация `limit/offset`
  (по умолчанию 50, «Показать ещё» в интерфейсе).
- `POST /api/operations` (админ/директор) — формы «+ Доход» / «+ Расход»:
  без фактической суммы создаётся ПЛАНОВАЯ операция на плановую сумму.

## Проекты и Excel (ШАГ 6)

Суммы проектов считаются из БД (seed заводит «входящие остатки» под данные
примера — см. docs/CABINET_DIFF.md); статусы «Плановый/В работе» — по факту
платежей, «Завершён» — вручную. `GET /api/projects/:id/summary` — сводка
по статьям (в карточке проекта). Архив — `PATCH /api/projects/:id`.
Экспорт: `GET /api/export/report.xlsx` и `GET /api/export/projects.xlsx`
(кнопки «Excel» на экранах «План-Факт» и «Проекты»).

## Администрирование (ШАГ 7)

- «Настройки → Пользователи» (только админ): создание с временным паролем
  (показывается один раз), блокировка/разблокировка
  (`GET/POST /api/users`, `PATCH /api/users/:id`).
- «Настройки → Общие настройки»: ставка компенсации км (PATCH /api/settings).
- «Настройки → Курсы валют»: `GET/POST /api/rates` — курс к TJS на дату;
  используется при одобрении валютных заявок и вводе операций.
- «Настройки → История действий» (только админ): аудит-лог `GET /api/audit`.
- «Настройки → Мой профиль»: смена пароля.

Проверка после деплоя (дополнительно к сценарию выше):

```bash
# вложение: загрузить и скачать (токен бухгалтера)
curl -s -X POST http://localhost/api/uploads -H "Authorization: Bearer <ACCESS>" \
```

# ЭТАП 2: задачи, планирование, закупки, склад, клиенты, уведомления

Пункты меню «Задачи», «Планирование», «Склад» и «Клиенты» перестали быть
заглушками, а «Закупки» переехали с фикстур прототипа на реальные данные.

## Задачи

- `GET /api/tasks?status=&project=&assignee=` — список; бухгалтер **всегда**
  видит только назначенные ему задачи (параметр `assignee` игнорируется).
- `POST /api/tasks`, `DELETE /api/tasks/:id` — админ и директор.
- `PATCH /api/tasks/:id` — руководители правят карточку целиком, исполнитель
  меняет только статус своей задачи (остальные поля отбрасываются на сервере).
- Статусы: `open` → `in_progress` → `done` (плюс `canceled`).
- Экраны: «Задачи» в админ-панели и «Мои задачи» в кабинете бухгалтера —
  один компонент с разным набором действий по роли.

`GET /api/users/assignees` (админ и директор) — список исполнителей: только
имя и роль, без контактов. Полный `GET /api/users` по-прежнему только у админа.

## Планирование

- `GET /api/plans?period=YYYY-MM` — плановые суммы месяца по паре
  «статья + проект» с подтянутым фактом; `POST /api/plans` — ввод/правка
  (upsert по паре), `DELETE /api/plans/:id` — удаление.
- Это та самая база сравнения для отчёта «План–Факт» (ТЗ, п. 7): после
  правки плана панель и отчёт перечитываются автоматически.

## Закупки (сделки)

- `GET/POST /api/deals`, `PATCH/DELETE /api/deals/:id` — админ и директор.
- Номер выдаётся автоматически: «СД-001», «СД-002»…
- Сумма позиции считается как `кол-во × цена × (1 − скидка/100)`, суммы
  хранятся в дирамах.
- **Завершение сделки** (`status: done`) приходует на склад позиции, у которых
  выбран товар из справочника — по одному движению `in` на позицию с
  комментарием «Приход по сделке СД-XXX». Закрытая сделка не редактируется и
  не удаляется (422 `deal_closed`) — её можно только отменить.

## Склад

- `GET /api/stock` — остатки: сумма приходов минус списания, плюс признак
  `low` (остаток ниже минимального).
- `GET /api/stock/moves?good=` — история движений;
  `POST /api/stock/moves` — приход или списание вручную.
  Списание больше остатка отклоняется: 422 «На складе только N шт».
- `PATCH /api/stock/goods/:id` — артикул, единица, минимальный остаток.
- Входящие остатки заводит seed (движение «Входящий остаток склада»).

## Клиенты

- `GET /api/clients` — контрагенты с оборотами по подтверждённым операциям
  и числом сделок; `PATCH /api/clients/:id` — тип (клиент / поставщик /
  оба), ИНН, телефон, почта, адрес, контактное лицо, комментарий.
- Сам список контрагентов ведётся в «Справочниках» — здесь только карточка.

## Уведомления

`GET /api/notifications` — колокольчик в шапке (и админ-панели, и кабинета).
Состав зависит от роли:

- админ и директор: заявки, ждущие решения; просроченные плановые платежи;
  товары ниже минимального остатка;
- бухгалтер: решения по его заявкам (одобрена / отклонена);
- всем: свои задачи — просроченные и с сегодняшним сроком.

Счётчик на колокольчике — число событий; список перечитывается после
решения по заявке, сторнирования, правки плана и завершения сделки.

Проверка после деплоя:

```bash
# приход по сделке попадает на склад
curl -s -X PATCH http://localhost/api/deals/1 -H "Authorization: Bearer <ACCESS_ДИРЕКТОРА>" \
  -H 'Content-Type: application/json' -d '{"status":"done"}'   # → {"id":1,"closed":true}
curl -s http://localhost/api/stock -H "Authorization: Bearer <ACCESS_ДИРЕКТОРА>"
# бухгалтер не видит закупки, склад и клиентов
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/api/stock -H "Authorization: Bearer <ACCESS_БУХГАЛТЕРА>"  # → 403
```

# Журнал операций и отчёт: доработка под ТЗ п. 3.1–3.2

## Массовые действия (ТЗ, п. 3.2)

`PATCH /api/operations/bulk` (админ/директор):
`{"ids":[1,2],"action":"confirm|delete|project","projectId":12}` →
`{"updated":N,"skipped":M}`.

- `confirm` — подтверждает оплату; плановая строка становится фактом
  (`isPlan` снимается, статус `confirmed`);
- `delete` — мягкое удаление (`deletedAt`);
- `project` — перенос в другой проект (проект проверяется, иначе 422).

**Операции из одобренных заявок пропускаются** (`skipped`): по ТЗ п. 5
одобренная заявка неизменяема, её можно только сторнировать. Интерфейс
показывает это сообщением после действия.

## Карточка операции

`GET /api/operations/:id` — полные поля, сумма в валюте операции и курс на
дату (ТЗ, п. 8), признак `locked` (операция из заявки) и история изменений
из аудит-лога. В интерфейсе открывается кликом по строке журнала; из карточки
доступны те же действия для одной операции.

## Экспорт журнала

`GET /api/export/operations.xlsx` принимает **те же фильтры**, что и
`GET /api/operations` (`type`, `confirmed`, `date_from/to`, `account`,
`counterparty`, `article`, `project`, `amount_min/max`, `q`) и выгружает весь
отфильтрованный список постранично, а не только видимую страницу. Кнопка —
в меню «⋯» над журналом.

## Что ещё появилось на экране «Операции»

- Группы строк «Сегодня» / «Вчера и ранее» (при пустом дне — «Сегодня нет
  операций»), как в ТЗ.
- Иконка комментария у суммы, если у операции есть примечание.
- Меню «⋯»: экспорт и настройка колонок (Счёт, Тип, Контрагент, Статья,
  Проект можно скрыть).
- Состояние панели фильтров и набор колонок запоминаются в браузере
  пользователя (`localStorage`, ключи `ithona.ops.*`).
- Колонка «Сумма» закреплена справа — при горизонтальной прокрутке цифра
  остаётся на виду.

## Детализация статьи в отчёте (ТЗ, п. 3.1)

Клик по строке отчёта «План–Факт» открывает операции этой статьи за выбранный
период (по строке проекта — с фильтром по проекту). Значок «▸» по-прежнему
разворачивает разбивку по проектам.

Проверка после деплоя:

```bash
# массовое подтверждение (директор)
curl -s -X PATCH http://localhost/api/operations/bulk -H "Authorization: Bearer <ACCESS>" \
  -H 'Content-Type: application/json' -d '{"ids":[1,2],"action":"confirm"}'
# выгрузка журнала с фильтром
curl -s -o операции.xlsx "http://localhost/api/export/operations.xlsx?type=out&confirmed=true" \
  -H "Authorization: Bearer <ACCESS>"
```

# Проекты и печать отчёта (ТЗ п. 3.1, 3.3)

## Удаление проекта

`DELETE /api/projects/:id` (админ/директор). По ТЗ п. 8 удалять то, на что
есть ссылки, нельзя: проект с операциями, планами, заявками, задачами,
сделками или движениями склада возвращает 422 `project_in_use` с перечнем,
что именно мешает, — такой проект можно только убрать в архив. Пустой проект
удаляется мягко (`deletedAt`), повторный запрос отдаёт 404.

## Показатель для анализа (ТЗ, п. 3.3)

Селектор над таблицей проектов переключает расчёт и заголовки колонок:

- **Прибыль методом начисления** — доходы и расходы вместе с неоплаченными
  обязательствами (плановые операции проекта);
- **Прибыль кассовым методом** — только подтверждённые платежи;
- **Движение денег** — те же подтверждённые суммы в виде
  «Поступления / Выплаты / Сальдо», без рентабельности.

## Фильтры проектов

Заработали параметры из прототипа: даты начала и окончания (проект попадает
в выборку, если начался не раньше и закончился не позже указанных дат) и
группа проектов; есть сброс параметров. Итоговая строка и суммы групп
считаются по выбранному показателю и действующим фильтрам.

## Печать и PDF

Кнопки «Печать» и «PDF» на экране «План-Факт» открывают системный диалог
печати (в нём же браузер сохраняет PDF). Печатная версия готовится стилями
`@media print` в `src/index.css`: сайдбар, шапка, панели кнопок и всплывающие
сообщения скрываются (`data-print-hide`), каркас `100vh` с внутренней
прокруткой распрямляется в обычный поток, сверху добавляется шапка документа
«IT-HONA LLC · Отчёт "План–Факт"» с периодом. Строки таблицы не разрываются
между страницами, фон бейджей печатается.

Проверка после деплоя:

```bash
# занятый проект удалить нельзя
curl -s -X DELETE http://localhost/api/projects/1 -H "Authorization: Bearer <ACCESS>"
# → {"error":{"code":"project_in_use","message":"Проект используется (…) — его можно только убрать в архив"}}
```

# Сделка закупки: частичные оплаты и поставки

Карточка сделки из прототипа заработала целиком: видно, сколько мы уже
заплатили поставщику и сколько он уже отгрузил.

## Выплаты

- `GET /api/deals/:id/payment-candidates?limit=` — расходные операции журнала,
  ещё не привязанные ни к одной сделке (если у сделки указан поставщик —
  только его операции).
- `POST /api/deals/:id/payments` `{"operationIds":[1,2]}` — прикрепить.
  Приход вместо выплаты — 422 `not_expense`; операция уже в другой сделке —
  422 `already_linked`.
- `DELETE /api/deals/:id/payments/:operationId` — открепить; сама операция
  остаётся в журнале.

Сумма выплат идёт в поле `paid`, остаток долга считается как
`сумма сделки − оплачено` («Мы должны»).

## Поставки

- `POST /api/deals/:id/deliveries` — документ получения:
  `{"date","isPlan","entityName","projectId","positions":[{"name","goodId","qty","unit","price"}]}`.
  Позиции с товаром из справочника **сразу приходуются на склад**; плановая
  поставка (`isPlan: true`) — только документ, склад не трогает.
- `DELETE /api/deals/:id/deliveries/:deliveryId` — удаление вместе с приходами:
  движения склада связаны с поставкой полем `delivery_id`, поэтому снимается
  ровно её приход.

Сумма поставок идёт в поле `delivered`, остаток обязательств поставщика —
`сумма сделки − поставлено` («Поставщик должен»).

## Когда товар попадает на склад

Приоритет у поставок: если по сделке оформлена хотя бы одна фактическая
поставка, при завершении сделки склад повторно не пополняется. Если поставки
не вели вовсе — при завершении приходуются все позиции сделки, как раньше.

Seed заводит демо-состояние сделки СД-001: аванс 12 000 TJS
(`deal:СД-001:pay1`) и поставку половины кабеля, чтобы карточка сразу
показывала частичную оплату и частичную отгрузку.

# Вложения к операциям и выгрузки по расписанию (ТЗ п. 10–11)

## Документы к операциям журнала

Раньше вложения были только у заявок кабинета. Теперь файл можно прикрепить
и к операции журнала:

- `POST /api/uploads` (теперь доступен и админу с директором) → ключ;
- `POST /api/operations/:id/attachments` `{"key","fileName","mime","size"}` —
  прикрепить; повторное имя у одной операции даёт 422 `file_exists`;
- `DELETE /api/attachments/:id` — открепить (файл в хранилище остаётся);
- `GET /api/operations/:id` возвращает список `attachments`.

Права: вложения операций видят только админ и директор — как и сам журнал;
бухгалтер по-прежнему видит вложения **своих** заявок. Если ключ есть, а файла
в хранилище нет (сменили `STORAGE_DIR` или бакет), отдаётся 404
`file_missing`, а не 500.

**Превью в интерфейсе**: изображения показываются картинкой, PDF — встроенным
просмотрщиком, из окна можно скачать файл. Превью работает и в карточке
операции, и в шторке расхода, и в истории кабинета.

## Выгрузки по расписанию

Экран: «Настройки → Выгрузки по расписанию» (админ и директор).

- `GET /api/export/schedules` — расписания, готовые файлы, справочники видов
  и периодичностей, признак `mailConfigured`;
- `POST /api/export/schedules` `{"kind","frequency","hourUtc","email"}` —
  вид: `report | projects | operations`, периодичность:
  `daily | weekly | monthly`, час запуска — по UTC;
- `PATCH /api/export/schedules/:id` — периодичность, час, почта, вкл/выкл;
- `DELETE /api/export/schedules/:id`;
- `POST /api/export/schedules/:id/run` — сформировать немедленно;
- `GET /api/export/files/:id` — скачать готовый файл.

Планировщик — таймер внутри приложения: раз в минуту берёт расписания, у
которых наступил срок, строит книгу Excel теми же функциями, что и кнопки
«Excel», кладёт файл в объектное хранилище и записывает в список. Отключается
переменной `EXPORT_SCHEDULER=off`.

**Почта.** Если заданы `SMTP_HOST` и `SMTP_FROM`, файл уходит письмом на
указанный адрес (дополнительно: `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`,
`SMTP_PASSWORD`). Без них письма не отправляются — файл просто копится в
панели, и интерфейс честно об этом пишет. `deploy.sh` заводит эти переменные
пустыми, чтобы их можно было заполнить в `/opt/app/.env` и перезапустить
backend.

Проверка после деплоя:

```bash
# создать еженедельную выгрузку отчёта и сразу сформировать её
curl -s -X POST http://localhost/api/export/schedules -H "Authorization: Bearer <ACCESS>" \
  -H 'Content-Type: application/json' -d '{"kind":"report","frequency":"weekly","hourUtc":6}'
curl -s -X POST http://localhost/api/export/schedules/1/run -H "Authorization: Bearer <ACCESS>"
```

# После обновления в браузере остаётся старый интерфейс

Симптом: `deploy.sh` отработал без ошибок, миграции применились, `/api/health`
отвечает `ok`, но на экране всё тот же интерфейс, что и до обновления.

Причина — кэш браузера. Vite кладёт хэш в имя JS-бандла
(`assets/index-QhA_4DJ6.js`), поэтому ассеты можно кэшировать надолго. Но
`index.html`, который на эти бандлы ссылается, кэшировать нельзя: браузер, не
получив от сервера никаких указаний, применяет к нему эвристическое кэширование
и продолжает открывать прежнюю версию страницы со ссылками на прежние бандлы.
Файлы на сервере при этом уже новые — их просто никто не запрашивает.

В `deploy/nginx-frontend.conf` это закрыто явными заголовками:

| Путь | Cache-Control |
| --- | --- |
| `/assets/…` | `public, max-age=2592000, immutable` |
| `/index.html` и любой SPA-маршрут | `no-cache, no-store, must-revalidate` |

Заголовок для ассетов задаётся одним `add_header` — пара `expires 30d` +
`add_header Cache-Control` отдавала `Cache-Control` дважды, потому что
`expires` добавляет собственный заголовок.

Конфиг вкомпилирован в образ (`COPY deploy/nginx-frontend.conf` в `Dockerfile`),
поэтому применяется при пересборке фронтенда — её делает сам `deploy.sh`
(`up -d --build backend frontend`). Отдельных действий не требуется.

Проверка заголовков на сервере:

```bash
curl -sI http://localhost/ | grep -i cache-control
# → Cache-Control: no-cache, no-store, must-revalidate

curl -sI "http://localhost/$(curl -s http://localhost/ \
  | grep -o 'assets/[^"]*\.js' | head -1)" | grep -i cache-control
# → Cache-Control: public, max-age=2592000, immutable
```

Страницу, закэшированную до этого исправления, браузер отдаёт из своего кэша и
на сервер не ходит — её нужно один раз перезагрузить принудительно:
**Ctrl+Shift+R** (Windows/Linux) или **Cmd+Shift+R** (macOS). Дальше обновления
подхватываются сами.

# Одна валюта учёта (решение заказчика)

Заказчик закрыл блокирующую развилку дизайн-пакета в пользу варианта
**«одна валюта, без пересчёта»**: все суммы в сомони, курсы не применяются.
Это отменяет п. 1 и п. 8 ТЗ («справочно USD, EUR, RUB, CNY с курсом на дату
операции») — так и задумано, решения заказчика главнее ТЗ.

**Структура БД не тронута.** Колонки `currency_code`, `rate`, `rate_date` и
`amount_tjs_dirams` остались на месте и заполняются `TJS` / `1` / суммой.
Таблицы `currencies` и `exchange_rates` тоже целы. Удалять их не стали:
экономии нет, а возврат к мультивалютности при закупках у зарубежных
поставщиков — реальный сценарий, и он не должен требовать обратной миграции.

Переключатель — по одной константе с каждой стороны:

| Файл | Константа |
| --- | --- |
| `server/src/currency.ts` | `SINGLE_CURRENCY` |
| `src/lib/currency.ts` | `SINGLE_CURRENCY` |

Что делает включённый режим:

- API принимает только `TJS`; операция или заявка в другой валюте отклоняется
  с 422 `currency_disabled`. **Валюту не подменяем молча** — «1000 USD» иначе
  превратилось бы в 1000 сомони: цифра та же, смысл другой;
- из формы операции убраны селектор валюты, поле курса и предпросмотр
  «Сумма в сомони» — введённая сумма и есть итог, вместо них подпись
  «Суммы в сомони (TJS)»;
- в заявке на оплату и расходе на авто вместо селектора — неизменяемая
  подпись `TJS`;
- вкладка «Курсы валют» в настройках скрыта (сам экран цел, он вернётся
  вместе с мультивалютностью).

Проверка на живом API:

```bash
# операция в долларах отклоняется
curl -s -X POST http://localhost/api/operations \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"date":"2026-08-01","type":"out","amount":100,"currency":"USD","articleName":"Проверка"}'
# → 422 {"error":{"code":"currency_disabled","message":"Учёт ведётся в сомони (TJS) …"}}

# она же в сомони проходит
curl -s -X POST http://localhost/api/operations \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"date":"2026-08-01","type":"out","amount":100,"articleName":"Проверка"}'
# → 201
```

# Правило расхода: факт по оплате поставщику

Вторая закрытая развилка: **расход становится фактом в момент оплаты
поставщику**, а не приёмки товара и не выдачи со склада. План-Факт при этом
сходится с банковской выпиской.

Как это устроено:

| Событие | Что создаётся | Влияет на План-Факт |
| --- | --- | --- |
| Поставка (`deliveries`) | только `stock_moves` | нет |
| Закрытие сделки без поставок | только `stock_moves` | нет |
| Выплата поставщику | `operations{type:'out', is_plan:false}` + `deal_id` | **да, это факт** |
| Одобрение заявки | `operations{type:'out', is_plan:true}` | план, не факт |

Правило легко сломать случайно: модуль поставок живой и продолжает создавать
складские движения — достаточно один раз добавить туда создание операции,
и факт начнёт расти по дате приёмки. Поэтому оно закрыто регресс-проверкой:

```bash
cd /opt/app/app/server
API=http://localhost/api ADMIN_PASSWORD=… npm run check:expense
```

Проверка создаёт сделку с позицией, оформляет поставку, проводит выплату
и убирает всё за собой. Пять утверждений:

```
  ok   поставка не создаёт факт расхода — факт 1253500 → 1253500 TJS
  ok   поставка приходует товар на склад — остаток 2 → 5
  ok   выплата увеличивает факт на свою сумму — факт 1253500 → 1255000 TJS
  ok   уборка вернула факт к исходному — 1253500 = 1253500 TJS
  ok   уборка вернула остаток к исходному — 2 = 2
```

Открытый вопрос, который этим решением **не закрыт**: считается ли фактом
неподтверждённая выплата. Сейчас факт — любая операция с `is_plan = false`
независимо от `status`, а метрика «Деньги» берёт только `confirmed`.
Это две разные цифры за один месяц (см. `docs/PLAN_UPDATE.md`, вопрос 3).

# Токены дизайн-системы

`src/tokens.css` — копия `it-hona/tokens.css` из дизайн-пакета, значения не
менялись. Подключается первым, до `index.css`. Это источник истины по цветам,
шрифтам, радиусам и плотности: **хексов в коде экранов больше нет**, только
переменные `--fin-*`.

## Что сведено

Проект накопил семьдесят три оттенка там, где в системе их около двадцати.
Соседние серые различались на один-два пункта и роли не несли. Сведено так:

| Было | Стало | Почему |
| --- | --- | --- |
| `#E7E5E0` `#E0DED8` `#DFDCD6` `#DDDAD3` `#DAD7D0` `#D8D5CE` `#C7C4BC` `#CFCCC4` … | `--fin-border` | рамка в системе одна |
| `#F3F2ED` `#F0EFEA` `#EFEDE8` `#EFEEE9` `#EDEBE6` … | `--fin-divider` | слабый разделитель один |
| `#FAF9F6` `#FBFBF9` `#FBFAF8` `#FAFAF8` `#F7F6F3` `#F4F8F5` … | `--fin-surface-alt` | подложка одна |
| жёлтый `#8A6A00/#FAF2D8` и оранжевый `#B25313/#FBECDE` | `--fin-warn` | цвет предупреждения в системе один |
| синий `#2A4D9B` и `#3E6B8A` (кабинет) | `--fin-accent` | своего синего в системе нет |

Правило дизайн-системы: «в системе четыре зелёных, и все заняты. Новый статус
берёт существующий цвет или получает нейтральный серый». Поэтому жёлтый
с оранжевым слились в один «внимание», а синий кабинета — в акцент. Смысл
статуса несёт подпись, а не оттенок: цветом одним, без подписи, статус
не передаётся никогда.

Ключи `yellow`, `orange`, `blue` в `C` (src/theme.ts) оставлены псевдонимами —
полсотни мест вызова править не пришлось, они просто указывают на те же токены.

Точка бейджа теперь красится тем же цветом, что и текст: отдельного оттенка
для точки в системе нет.

## Что исправилось попутно

Кабинет и админ-панель красили одни и те же статусы по-разному — ранние
прототипы рисовались отдельно. Теперь оба берут пять состояний из одной
палитры, а статус проекта везде один: **«Плановый» нейтральный, «В работе»
акцентный, «Завершён» зелёный** (раскладка из дизайн-системы). До этого
админ-панель показывала «Плановый» синим и «В работе» жёлтым, а кабинет —
«В работе» зелёным и «Завершён» серым.

## Плотность

Два режима из токенов: комфортный по умолчанию и компактный через
`:root[data-fin-density="compact"]`. Меняются высота строки (44 → 36px),
поля ячейки, высота контролов (40 → 34px) и размеры шрифта (14 → 12.5px).

Раньше плотность жила в двух своих переменных (`--row-pad`, `--card-pad`) и
меняла только отступы — половина значений оставалась комфортной. Теперь
`applyThemeVars` выставляет атрибут `data-fin-density` на корне документа,
а `--row-pad` / `--card-pad` выражены через токены плотности, поэтому старый
код экранов продолжает работать и пересчитывается вместе со всем остальным.

Переключатель плотности в интерфейсе появится вместе с вкладкой «Компания»
в настройках (задача № 6 плана).

# Кабинет директора: согласование заявок

Главный экран роли «директор» — макет `IT-HONA Кабинет директора.dc.html`.
До этого согласование жило строкой в общем «списке внимания» на панели.
Открывается пунктом меню **«Заявки на утверждение»** — он первый в разделе
«Панель управления» и несёт счётчик очереди. Бухгалтеру пункт не показывается.

## Раскладка

Двухколоночная: очередь слева, разбор справа (420px — как в README пакета;
в самом файле макета панель 340px, взято значение из README). Сверху три
счётчика: сколько заявок ждёт, на какую сумму, сколько дней самая старая.

Сумма в счётчике считается **без поездок** — они измеряются километрами,
и складывать их с сомони нельзя.

## Решения

**Быстрые действия прямо в строке** — «галочка» и «крестик» 30×30. Заявка
на бензин за 340 сомони не требует изучения: она закрывается одним нажатием,
без открытия карточки.

**Массовое одобрение.** Чекбоксы в строках включают панель с числом выбранных
и суммой. `PATCH /api/requests/approve-many` проверяет каждую заявку теми же
правилами перехода статуса, что и одиночное решение, поэтому непригодная
(черновик, уже решённая) не роняет пачку — возвращается в `skipped` с причиной,
и директор видит, что прошло не всё:

```json
{"approved":2,"skipped":[{"id":10,"reason":"Недопустимый переход статуса: draft → approved"}]}
```

**Отклонение требует причину.** Четыре готовые формулировки плюс поле для
своей; кнопка «Отклонить заявку» неактивна, пока причина не выбрана.
Асимметрия намеренная: одобрение причины не требует. По ТЗ (п. 5) автор может
исправить отклонённую заявку и отправить снова — без причины он не знает,
что чинить.

**«Вернуть в очередь»** у решённой заявки — это сторнирование (ТЗ, п. 5):
одобренная заявка неизменяема, снять её можно только сторно.

## «Что меняется в цифрах»

Блок показывает последствие решения **до** нажатия. В макете это статичная
иллюстрация — здесь цифры настоящие, из сводки проекта.

Одобрение — не смена статуса, а бухгалтерское действие: по ТЗ (п. 8) оно
создаёт плановую операцию расхода, и та немедленно попадает в план проекта.

| Строка | Что показывает |
| --- | --- |
| План по проекту | растёт на сумму заявки |
| Осталось оплатить | план − факт: обязательство, которое ещё предстоит закрыть |
| Выполнение плана | факт / план; красным — только если после одобрения перерасход |

Вторая строка названа «Осталось оплатить», а не «свободный остаток», как
в макете: в план проекта входят и бюджет, и уже одобренные, но не оплаченные
заявки, поэтому одобрение увеличивает **обязательство**, а не уменьшает
свободные деньги. Формулировка макета в этой модели данных вводила бы
в заблуждение.

У поездки блок не показывается: её сумма считается на сервере по ставке
компенсации (`settings.km_rate`), и подставлять её в интерфейсе значило бы
показывать выдуманную цифру.

## Порядок роутов

`PATCH /requests/approve-many` объявлен **до** `PATCH /requests/:id` —
иначе Nest разбирает `approve-many` как идентификатор и `ParseIntPipe`
возвращает 400 вместо 403/200. Проверка на живом API это и поймала.

## Проверка

```bash
# массовое одобрение закрыто для бухгалтера
curl -s -o /dev/null -w "%{http_code}\n" -X PATCH http://localhost/api/requests/approve-many \
  -H "Authorization: Bearer $ACCOUNTANT" -H 'Content-Type: application/json' -d '{"ids":[1]}'
# → 403

# пустой список отклоняется
curl -s -X PATCH http://localhost/api/requests/approve-many \
  -H "Authorization: Bearer $DIRECTOR" -H 'Content-Type: application/json' -d '{"ids":[]}'
# → 422 {"error":{"code":"validation_error","message":"Не выбрано ни одной заявки"}}
```

Playwright — 22 проверки: счётчик в меню, три счётчика очереди, панель разбора
с номером заявки и историей, блок «Что меняется в цифрах», неактивная кнопка
отклонения без причины и активная после выбора, массовое одобрение (очередь
8 → 6 и тост о результате), вкладка «Решённые» со сторнированием, отсутствие
хексов, адаптив 360px и скрытый от бухгалтера пункт меню.

# Кабинет бухгалтера на телефоне

Макет `IT-HONA Мобильный сотрудника.dc.html` (375px). На узком экране обе
десктопные формы — «Заявки на оплату» и «Заявки на машину» — заменяет одна
форма с переключателем вида (`src/cabinet/MobileRequestForm.tsx`); списки
заявок под ней остаются прежними. На десктопе ничего не меняется.

## Что даёт вид заявки

| Вид | Поля | Вложение |
| --- | --- | --- |
| **Оплата** | проект, наименование (3–200), сумма | документ, необязательно |
| **Поездка** | проект, цель (3–120), километры, контрагент | **фото одометра обязательно** |
| **Расход на авто** | проект, категория, сумма | **чек обязателен от 100 TJS** |

Сумма — первое и самое крупное поле (40px, по центру, цифровая клавиатура):
её знают наизусть, остальное выбирается из списков. Переключение вида
очищает форму — набор полей другой, и подставлять старые значения незачем.

## Подпись кнопки называет недостающее поле

Серая кнопка без объяснения — самая частая причина брошенной формы.
Порядок проверок повторяет порядок полей на экране, поэтому подпись
указывает на ближайшее незаполненное:

```
Укажите сумму → Впишите наименование → Выберите проект → Отправить директору
Укажите километры → Впишите цель поездки → Выберите проект → Нужно фото одометра
Укажите сумму → Выберите проект → Выберите категорию → Нужен чек — сумма от 100 TJS
```

## Порог 100 TJS виден до отправки

При переходе суммы через порог рамка кнопки загрузки становится охристой
пунктирной, подсказка под ней меняется с «До 100 TJS чек можно не
прикладывать» на «Чек обязателен: сумма 100 TJS и выше», а подпись кнопки
отправки — на «Нужен чек — сумма от 100 TJS». Правило ТЗ (п. 4.2) видно
в интерфейсе, а не срабатывает отказом сервера после нажатия.

## Цели нажатия

Минимум 44px, строки выбора 62px, кнопка отправки 54px. Вместо родного
`select` — шторка снизу со строками по 52px: попасть пальцем в пункт
системного списка на ходу тяжело.

**Расхождение с макетом:** переключатель вида в макете нарисован высотой
40px, что ниже минимума 44px из ТЗ (п. 6) и из README самого пакета.
Взято 44 — требование доступности важнее пиксельного повторения.

трёх видов, шторки выбора проекта и категории, поведение порога 100 TJS
в обе стороны, отсутствие горизонтальной прокрутки и хексов, все цели

# Настройки: права и компания

Макет `IT-HONA Настройки.dc.html`. К существующим вкладкам добавлены две.

## Вкладка «Права»

Матрица «роль × действие», **только для чтения**. Права зашиты в роль —
отдельной сущности «право» в системе нет, и редактируемые галочки создали бы
состояния, которых бэкенд не проверяет.

Строки собраны не из ТЗ, а из того, что реально проверяет сервер: у каждого
маршрута стоит `@Roles(...)`, и таблица его повторяет. Это важно — таблица,
собранная из ТЗ, разошлась бы с поведением при первой же правке гвардов.

Метки: `✓` право есть, `—` нет, `частично` (бухгалтер видит только суммы
своих заявок), `?` в ТЗ не описано.

Из четырёх ячеек, помеченных в макете вопросом, три закрыты:

| Вопрос макета | Ответ |
| --- | --- |
| Видит ли директор План-Факт целиком | да, все проекты компании (заказчик) |
| Кто принимает товар на склад | администратор; роль «Кладовщик» снята заказчиком |
| Может ли администратор создавать заявки | нет — `@Roles('accountant')` |
| Может ли администратор утверждать заявки | **открыт**: в коде да, в ТЗ не описано |

Последний остаётся вопросом и помечен на экране: ТЗ (п. 5) отдаёт решение
директору и молчит о его отсутствии. Сейчас утверждать может и администратор —
иначе очередь встаёт на время отпуска.

## Вкладка «Компания»

Профиль организации (название, города, валюта учёта, часовой пояс) и
**переключатель плотности**.

Плотность меняет весь набор из токенов — высоту строки, поля ячеек, высоту
контролов и размеры шрифта, — а не пару отступов. Рядом стоит живой пример
таблицы: он перестраивается вместе с переключателем, так что видно, что
именно меняется. Значение хранится в `localStorage` (`ithona.density`) и
применяется при старте обеих оболочек — админ-панели и кабинета.

Серверного профиля оформления в ТЗ нет, заводить его ради одного
переключателя незачем: настройка живёт на устройстве.

## Единственного администратора нельзя отключить или понизить

Иначе систему закрывают изнутри в два клика и войти в настройки больше
некому. Проверка **на сервере**, а не только замок в строке:

```bash
# один активный администратор
curl -s -X PATCH http://localhost/api/users/1 \
  -H "Authorization: Bearer $ADMIN" -H 'Content-Type: application/json' \
  -d '{"role":"director"}'
# → 422 {"error":{"code":"last_admin","message":"Это единственный администратор …"}}

# при двух администраторах ограничение не срабатывает
curl -s -o /dev/null -w "%{http_code}\n" -X PATCH http://localhost/api/users/$SECOND \
  -H "Authorization: Bearer $ADMIN" -H 'Content-Type: application/json' \
  -d '{"active":false}'
# → 200
```

Отключить самого себя нельзя и раньше (`self_block`), поэтому вдвоём эти две
проверки закрывают все пути: последнего админа не отключить ни своей рукой,
ни чужой, ни понижением роли.

В интерфейсе строка такого администратора показывает запертую кнопку
«🔒 Единственный админ» — действие видно, но недоступно.

## Проверка

Playwright — 13 утверждений: матрица из 12 строк и трёх ролей без единого
редактируемого контрола, отметка открытого вопроса, профиль компании,
переключение плотности (44 → 36px, текст 14 → 12.5px), сохранение выбора
после перезагрузки, запертая строка единственного админа, отсутствие хексов
и адаптив 360px.

# Экспорт в Excel: шесть правил формата и выбор колонок

Макет `IT-HONA Экспорт в Excel.dc.html`. Из шести правил формата раньше
выполнялись три; закрыты остальные и добавлен диалог выгрузки.

| # | Правило | Как сделано |
| --- | --- | --- |
| 1 | Файл повторяет текущую выборку с фильтрами, а не всю базу | журнал выгружается постранично по тем же фильтрам, что на экране; сами фильтры записываются на лист «Параметры» |
| 2 | Числа выгружаются числами | тип колонки `money` → значение `number` + формат `#,##0.00` |
| 3 | Даты выгружаются датами | тип `date` → значение `Date` + формат `dd.mm.yyyy` |
| 4 | Валюта отдельной колонкой, без приведения | колонка «Валюта» во всех трёх выгрузках |
| 5 | Шапка закреплена, заголовок повторяется при печати | `views: frozen` + `pageSetup.printTitlesRow` |
| 6 | Второй лист — параметры выгрузки | лист «Параметры»: кто, когда, фильтры, состав колонок |

Дата пишется полднем локального дня, а не полуночью UTC: иначе часовой пояс
читающего сдвигает её на сутки назад, и 1 августа превращается в 31 июля.

Фильтры на листе «Параметры» записываются **именами, а не идентификаторами**:
«Проект: 12» через месяц никому ничего не скажет, поэтому справочные значения
подставляются из базы.

Файлы по расписанию тоже получают лист «Параметры» — с пометкой, что это
выгрузка планировщика и фильтры экрана к ней не применялись. Получатель
письма видит вложение без экрана, с которого его сняли.

## Диалог выгрузки

Кнопка «Excel» на «Проектах», в отчёте и в меню «⋯» журнала открывает диалог:
колонки снимаются чекбоксами, предпросмотр листа перестраивается, имя файла и
оценка размера пересчитываются.

**Ключевые колонки заблокированы** — без даты, статьи и суммы журнал операций

добавляет их в файл независимо от того, что прислал клиент: ограничение
живёт в `COLUMNS`, а не в интерфейсе.

Имя файла несёт дату и пометку о неполном составе:
`операции-2026-08-01-9из10.xlsx`. Имя приходит с сервера в
`Content-Disposition`, браузер сохраняет ровно его.

Состав колонок отдаётся отдельным маршрутом:

```bash
curl -s http://localhost/api/export/columns -H "Authorization: Bearer $TOKEN"
# → {"kinds":[{"code":"operations","name":"Журнал операций","columns":[
#      {"key":"date","title":"Дата","locked":true,"type":"date"}, …]}]}
```

# Уведомления

Макет `IT-HONA Уведомления.dc.html`. Раньше был только колокольчик со списком;
добавлен экран ленты и — главное — состояние «прочитано».

## Почему отдельной таблицы событий нет

Лента считается **из данных**: заявки в очереди, остатки ниже минимума,
просроченные плановые платежи, задачи на сегодня. Дублировать это строками
значило бы держать вторую копию правды и следить за её устареванием: заявку
одобрили — уведомление о ней должно исчезнуть само, а не ждать чистки.

Хранится только то, чего из данных не вывести: **прочёл ли конкретный человек
конкретное событие**. Таблица `notification_reads` — пара «пользователь + ключ
события» (`req:12`, `stock:3`, `task:7`) и время. Ключи устойчивы, потому что
выводятся из идентификатора записи.

## «Прочитано» принадлежит пользователю

Правило из пакета: директор прочитал — у бухгалтера уведомление осталось
непрочитанным. Проверяется на двух учётных записях:

```bash
# у обоих по 5 непрочитанных
curl -s $API/notifications -H "Authorization: Bearer $DIRECTOR"   # count: 5
curl -s $API/notifications -H "Authorization: Bearer $ADMIN"      # count: 5

# директор отмечает одно
curl -s -X POST $API/notifications/read -H "Authorization: Bearer $DIRECTOR" \
  -H 'Content-Type: application/json' -d '{"keys":["req:17"]}'    # {"read":1}

curl -s $API/notifications -H "Authorization: Bearer $DIRECTOR"   # count: 4
curl -s $API/notifications -H "Authorization: Bearer $ADMIN"      # count: 5 ← не изменилось
```

`POST /api/notifications/read` без ключей отмечает всю ленту пользователя.
Повторная отметка того же ключа безвредна (`skipDuplicates`), а ключи не
проверяются на существование: событие могло исчезнуть, пока человек читал —
заявку одобрил кто-то другой, — и отметка о нём никому не мешает.

## Экран

Пункт «Уведомления» в меню панели и в кабинете; в выпадающем списке
колокольчика — переход «Все уведомления →».

- две вкладки: «Непрочитанные» и «Все» со счётчиками;
- группировка по дням: «Сегодня», «Вчера», «Ранее»;
- непрочитанные выделены подложкой, жирным заголовком и точкой;
- «Прочитать все» одной кнопкой.

**Счётчик колокольчика теперь показывает только непрочитанные.** Раньше он
считал всю ленту, поэтому цифра не гасла никогда и перестала что-либо значить.

**Уведомление ведёт к действию** — правило пакета. Клик открывает не список,
а нужный экран: заявка → очередь согласования (у бухгалтера — его история),
остаток → склад, план → планирование, задача → задачи. Заодно уведомление
помечается прочитанным.

## Проверка

Playwright — 15 утверждений: счётчик, переход из колокольчика, группировка по
дням, точки у непрочитанных, переход по клику на верный экран, уменьшение
счётчика, разделение вкладок, «прочитать все», пустое состояние, адаптив

**после того как директор обнулил свой счётчик, у руководителя осталось 5
непрочитанных**.

# Состояния: загрузка, пустота, ошибки

Макет `IT-HONA Состояния.dc.html`. Общие компоненты — `src/components/states.tsx`.

## Скелетоны вместо надписи «Загрузка…»

Пульсирующая заглушка держит раскладку, поэтому при появлении данных страница
не прыгает. `SkeletonTable`, `SkeletonCards`, `SkeletonLine` считают высоту
строки из токенов плотности, то есть в компактном режиме скелетон тоже
компактный.

## Пустые состояния называют действие

Правило пакета: пустое состояние называет действие («Добавьте первый проект»),
а не констатирует пустоту («Нет данных»). Кнопка — глагол и результат: ведёт
туда, где пустота исчезнет.

Важно различать **два разных пустых состояния**, которые раньше выглядели
одинаково:

| Ситуация | Что показываем |
| --- | --- |
| Данных ещё нет | «Операций пока нет» + кнопка «Добавить расход» |
| Фильтр не совпал | «Под фильтры ничего не подошло· Данные есть, но не в этой выборке» + «Сбросить фильтры» |
| Всё разобрано | «Задач нет · ничего не назначено и не просрочено» (зелёный тон) |

Заменены формулировки, которые правило запрещает: «Ничего не найдено»,
«Задач нет», «Позиций пока нет», «Свободных выплат нет» — на складе, у
клиентов, в задачах и в закупках.

## Ошибки

Четыре правила текста из пакета:

1. **Без «Упс» и восклицаний.** Это бухгалтерия: человек хочет знать, потеряны
   ли деньги, а не читать шутку. «Журнал не загрузился», а не «Упс! Что-то
   пошло не так».
2. **Сразу о сохранности.** Первый вопрос при ошибке — «я потерял то, что
   вводил?». Отвечаем до того, как спросят: «Данные на месте — не отобразился
   только список. Фильтры и настройки сохранены».
3. **Техника — под «Подробности».** Код и сообщение сервера нужны поддержке,
   не бухгалтеру. Скрыты до нажатия, с кнопкой «Скопировать для поддержки».
4. **Не блокировать весь экран.** Упал список — гаснет список, а не страница:
   фильтры, сайдбар и остальные цифры человеку ещё нужны.

Прежний красный тост «Не удалось загрузить данные» на всю ширину заменён
карточкой с «Повторить», «Подробности» и текстом о сохранности.

## Проверка

Playwright — 19 утверждений. Ошибка воспроизводится подменой ответа сервера
на 500, загрузка — задержкой ответа:

```
  ok   на первой загрузке показан скелетон
  ok   без «Упс» и восклицательных знаков — Журнал не загрузился
  ok   сказано о сохранности введённого — Данные на месте …
  ok   фильтры остались доступны
  ok   сайдбар остался доступен
  ok   техника скрыта до нажатия
  ok   «Подробности» раскрывают текст сервера — Внутренняя ошибка сервера
  ok   после «Повторить» ошибка ушла
  ok   не констатирует пустоту, а объясняет — Под фильтры ничего не подошло
  ok   кнопка — глагол и результат — Сбросить фильтры
  ok   кнопка возвращает данные
```

# Резервные копии базы

Их не было — это была самая опасная дыра во всей установке: одно неудачное
восстановление, сбой диска или ошибочный `DROP` стоили бы всей базы, а
снапшотов у хостера нет.

`deploy.sh` теперь ставит ежедневное копирование сам, отдельных действий не
требуется.

## Как устроено

| Что | Где |
| --- | --- |
| Скрипт | `/opt/app/backup-db.sh` (из `deploy/backup-db.sh`) |
| Копии | `/opt/app/backups/ithona-ГГГГ-ММ-ДД_ЧЧММ.dump`, права 600 |
| Расписание | systemd-таймер `ithona-backup.timer`, ежедневно 03:30 ±15 мин |
| Хранение | 14 дней, дальше ротация; меняется `BACKUP_KEEP_DAYS` |

Формат — `pg_dump -Fc` (кастомный, сжатый): восстанавливается выборочно и
меньше зависит от версии клиента, чем текстовый.

Первая копия снимается **сразу при деплое** — таймер сработает только ночью,
а точка отката нужна до правок, не после.

## Защита от «копии, которой нет»

Пустой или обрезанный дамп хуже отсутствия: он создаёт ложное чувство
защищённости. Поэтому скрипт:

- пишет во временный файл `*.part` и переименовывает только по успеху —
  прерванный дамп никогда не выглядит готовым;
- отбраковывает файл меньше 1 КБ;
- проверяет заголовок `PGDMP`;
- **удаляет старые копии только после того, как новая сохранена.**

## Проверка вручную

```bash
sudo /opt/app/backup-db.sh
# [backup] снимаю дамп в /opt/app/backups/ithona-2026-08-01_1612.dump
# [backup] готово: … (192 КБ)
# [backup] копий в /opt/app/backups: 1, всего 192K

systemctl list-timers ithona-backup.timer    # когда следующий запуск
journalctl -u ithona-backup.service -n 20    # что было в прошлый раз
```

## Проверка, что копия восстанавливается

Копия, которую никто не пробовал развернуть, — не копия, а надежда.

```bash
sudo /opt/app/app/deploy/check-restore.sh
```

Скрипт берёт самый свежий дамп, разворачивает его во **временную** базу рядом
с рабочей (рабочую не трогает) и сверяет строки и суммы:

```
  ok   копия найдена — ithona-2026-08-01_1612.dump, 192 КБ
  ok   заголовок PGDMP на месте — формат pg_dump -Fc
  ok   таблица users — 7 = 7 строк
  ok   таблица operations — 77 = 77 строк
  ok   суммы операций совпадают — 1170773250 дирам
  ok   история миграций восстановлена — 11 = 11
```

Сверка истории миграций важна отдельно: без таблицы `_prisma_migrations`
восстановленная база не совпадёт по версии со схемой, и `migrate deploy`
попытается применить всё заново.

## Восстановление

```bash
# 1. Остановить бэкенд, чтобы никто не писал в базу во время восстановления
cd /opt/app && docker compose stop backend

# 2. Развернуть копию поверх рабочей базы
DB=$(sed -n 's/^DATABASE_URL=//p' /opt/app/.env | tail -1)
docker compose exec -T postgres pg_restore --clean --if-exists --no-owner --no-acl \
  -d "$DB" < /opt/app/backups/ithona-2026-08-01_1612.dump

# 3. Поднять обратно и проверить
docker compose start backend
curl -s http://localhost/api/health
```

Флаг `--clean --if-exists` удаляет существующие объекты перед восстановлением;
без него `pg_restore` упрётся в уже существующие таблицы.

## Чего эти копии не закрывают

Они лежат **на том же диске**, что и база. От случайного удаления данных и
неудачной миграции защищают, от потери сервера — нет. Для этого копии нужно
увозить наружу: `scp` по расписанию на другую машину, S3 или снапшоты
хостера. Это следующий шаг, и его стоит сделать до боевой эксплуатации.
